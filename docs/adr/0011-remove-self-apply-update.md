# ADR-0011: アプリ自身による更新の自己適用（ダウンロード・上書き）を廃止する

- ステータス: 承認済み
- 決定日: 2026-08-06
- 決定者: 中村勝（株式会社フェローテック）
- 関連: ADR-0003（Velopack採用）, ADR-0008（更新適用と再起動のレース対策）,
  ADR-0009（Program Files per-machine化・更新の同意必須化）, ISS-007, ISS-008

## 背景

v0.3.1（Program Files per-machine 化・MSI配布・ADR-0009適用後）のリリースで、
実機において以下の障害が再発した。

```
System.IO.FileLoadException: Could not load file or assembly
'C:\Program Files\Ferrotec.MDAsisst\current\MDAsisst.dll'. アクセスが拒否されました。
```

切り分けの結果、次の事実が確認された。

- **オンライン自動更新（アプリ内の「更新を確認」→同意→ダウンロード→`ApplyAndRestart`）を
  実行した直後にのみ発生する。**
- 同じ端末に **MSI をクリーンインストールした場合は正常に起動する。**

すなわち、初回インストール（MSI、Windows Installerサービス経由）は問題ないが、
**その後にアプリ自身が行う「更新の自己適用」だけが失敗する**という構造が明らかになった。

Velopack公式ドキュメントで確認したところ、インストール方式（Setup.exe / MSI）に関わらず、
更新の適用は常にVelopack自身の `Update.exe`（＝アプリ自身の権限・経路）が
`current` フォルダのファイルを直接上書きする実装であり、**MSIの信頼された配置経路を
更新時には経由しない**ことが分かった。

ADR-0009 は「配置場所を `%LocalAppData%` から Program Files に変える」ことで
ISS-008（EDRの誤検知）に対処したが、これは的の半分にしか当たっていなかった。
EDR（Cybereason）が警戒するパターンは本質的に

1. 未署名の実行ファイルが
2. 自分自身の実行ファイル・DLLを
3. 自己書き換えする

という**挙動そのもの**であり、書き換え先が Program Files であっても、
書き換え主体がアプリ自身である限りこのパターンは解消されない。Program Files への
書き込みには管理者権限が必要なため、Velopack は書き込み不可時に自己昇格
（`run_process_as_admin`）して処理を続行する。この「未署名の常駐アプリが、
昇格した別プロセスとして自分自身の実行ファイルを書き換える」という一連の挙動が、
per-machine 化後もなお EDR の行動検知に該当し得ることを、今回の再発で確認した。

## 決定

**アプリ自身によるダウンロード・自己適用の経路を完全に廃止する。**

- `IUpdateService` から `DownloadAsync` / `ApplyAndRestart` を削除する。
  `VelopackUpdateService` は「新バージョンの有無を確認する」（`CheckAsync`）機能のみを持つ。
- 更新方式（自動／手動／不要）の意味を再定義する。
  - 「自動」「手動」: 新バージョンの有無を**確認・通知するだけ**。見つかった場合は
    確認ダイアログを表示し、同意した場合は既定のブラウザーで GitHub Releases ページを開く。
  - 「不要」: 従来どおり一切ネットワークアクセスを行わない。
- 実際の更新適用は、配布された `.msi` インストーラーの**手動再インストール**
  （ユーザー操作、またはIT部門による配布）に一本化する。MSIインストールは
  Windows Installerサービスという信頼された経路を経るため、ADR-0009が本来
  目指していた「信頼された経路での配置」を更新時にも一貫して保てる。

## 検討した代替案

| 案 | 却下理由 |
| --- | --- |
| 差分パッケージ（delta）を無効化し full のみ配布 | 今回の障害の根本原因（自己書き換えという挙動そのもの）を解消しない。差分起因の破損の可能性は排除できるが、EDR誤検知のリスクは残る |
| 適用後にDLLハッシュを検証しロールバックする仕組みを追加 | 実装コストが高く、かつ検証中に再度EDRの監視対象になり得る。応急処置に留まり恒久策にならない |
| コード署名を取得して自己更新を継続 | ADR-0009 の検討時と同様、署名の有無ではなく「どこで・誰が・どのように書き換えるか」が EDR 行動検知の主たる判定要素であるため、署名だけでは本質的解決にならない。ISS-001として別途優先度を再評価する |
| MSIを都度サイレント実行する自己更新（`msiexec /i ... /quiet`をアプリから起動） | 結局「アプリ自身が自分の更新処理を起動する」点は変わらず、EDRの警戒パターンから完全には外れない。加えてMSIのサイレント実行にも管理者権限昇格は必要 |

## 影響（既存要件・実装との差分）

- **FR-ST-05 / FR-ST-06 を変更**: 「確認・適用」から「確認・通知（リリースページへの誘導）のみ」に変更。
- **FR-ST-11 を新設**: 更新の適用はアプリが行わず、MSIの手動再インストールで行うことを明文化。
- `IUpdateService.DownloadAsync` / `ApplyAndRestart` を削除（`VelopackUpdateService`,
  `NullUpdateService` 双方から）。
- `MainWindow.RunUpdateFlowAsync` / `SettingsWindow.CheckUpdate_Click` を、
  通知ダイアログ→ブラウザーでリリースページを開く実装に変更。
- `docs/operation-manual.md` 6.3節・トラブルシューティング表を更新し、
  v0.3.0/v0.3.1 で発生した障害と対処法（アンインストール→MSI再インストール）を明記。
- ADR-0008（更新適用と再起動のレース対策）は、適用対象（`ApplyAndRestart`）自体が
  なくなったことで完全に凍結・歴史的記録となる。

## 今後の検討事項

- ISS-001（コード署名）は「EDR誤検知の直接対策にはならない」という結論を維持しつつ、
  SmartScreen警告抑止の観点で優先度を改めて評価する。
- 配布運用（IT部門によるMSIの一斉配布、社内ソフトウェア資産管理ツールとの連携）を
  別途整理する必要がある（次フェーズの課題）。
