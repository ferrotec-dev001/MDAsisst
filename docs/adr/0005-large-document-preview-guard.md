# ADR-0005: 超大規模文書ではリアルタイムプレビューを一時停止する

- ステータス: 承認済み（暫定策。恒久対策は継続検討）
- 決定日: 2026-08-05
- 起票: CI 上での性能テスト（NFR-04）失敗の調査

## 背景

`docs/requirements.md` NFR-04 は「10,000行の Markdown 編集時、入力からプレビュー反映まで
500ms 以内」と定めていた。実装後の単体テストで、10,000行の文書を FlowDocument へ
変換する処理が **CI 環境（GitHub Actions windows-latest）で約2.4秒**かかることが判明した
（テスト: `RendererTests.一万行の文書を継続入力中の再描画で500ミリ秒以内に描画できる`）。

原因は JIT ウォームアップではなく、**WPF の `DependencyObject` 1個あたりの生成コストが高い**
ことにある。10,000行の文書は見出し・リスト・強調等を含め数万個の `Paragraph`/`Run`/`Span` を
生成するため、単純な「入力のたびに全文書を作り直す」設計では大規模文書に対して原理的に
スケールしない。

## 決定（暫定策）

1. 編集中の行数が **5,000行を超えたら自動プレビュー更新を停止**し、ステータスバーで
   利用者に通知する（`MainWindow.UpdatePreview` の `LargeDocumentLineThreshold`）。
2. `Ctrl+Shift+P` で明示的に1回だけ再描画できるようにする（`ForceUpdatePreview`）。
3. これにより、超大規模文書の編集で **UI がフリーズする／編集不能になる事態を防ぐ**
   （NFR-05: オフラインでも完全動作する、と同様に「大文書でも操作不能に陥らない」を優先）。

## 未決事項（要ユーザー確認）

NFR-04 の「10,000行」という基準は初回要件ヒアリング時の想定であり、実際の利用シーンで
そこまで大きな単一 Markdown ファイルを編集するかは未確認。恒久対策には以下の選択肢があり、
いずれもそれなりの実装コストを伴うため、対象文書規模を再確認したうえで方針を決めたい。

| 選択肢 | 概要 | コスト |
| --- | --- | --- |
| A. 差分レンダリング | 変更のあった Markdown ブロックのみ FlowDocument を差し替える | 中〜大（AST 差分検出の実装が必要） |
| B. 仮想化 | 表示領域外のブロック生成を遅延させる | 中（スクロール連動の実装） |
| C. 対象規模の見直し | NFR-04 を現実的な規模（例: 2,000行）に見直し、超過時は本 ADR の一時停止策を正式仕様とする | 小（ドキュメント更新のみ） |

## 影響

- `docs/requirements.md` の NFR-04 は「本文の暫定策で緩和的に運用」と注記した。恒久対応方針が
  決まり次第、本 ADR と要件定義の双方を更新する。
